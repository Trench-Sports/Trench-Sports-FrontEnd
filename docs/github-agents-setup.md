# GitHub agents — Trench-Sports org setup

Three agent surfaces, in the order they should be turned on. Everything in
`.github/` and `REVIEW.md` is currently **untracked** — none of it is live on
GitHub yet, so step 0 is not optional.

| Surface | What it does | Where it's configured |
|---|---|---|
| Audit agents | 7 diff-scoped auditors on every PR into `main` | `.github/workflows/audit.yml` → org reusable workflow |
| Code Review | Generic correctness review, inline comments + check run | Claude admin settings (no workflow file) |
| `@claude` | On-demand: ask a question, turn an issue into a PR | `.github/workflows/claude.yml` |

---

## Step 0 — Commit what already exists

```bash
git add .github REVIEW.md
git commit -m "CI: audit agents, @claude workflow, review instructions"
```

`REVIEW.md` matters more than it looks. Code Review reads it from the default
branch and injects it verbatim as the highest-priority instruction block in
every review agent. Until it's on `main`, reviews fall back to generic
correctness defaults and the calibration in that file does nothing.

> Note: `git add .github` also stages `.claude/settings.local.json` if you're
> not careful with globs — that file is machine-local and should stay
> untracked. Check `git status` before committing.

## Step 1 — Create the org reusable workflow repo

`audit.yml` no longer contains the runner steps; it calls a shared workflow so
the next Trench-Sports repo gets the same scaffolding for free. The agents
themselves stay per-repo on purpose — see `.claude/agents/README.md`.

1. Create a new repo named exactly **`.github`** under the `Trench-Sports` org.
   The name is load-bearing: GitHub treats `ORG/.github` as the org-wide
   defaults repo.
2. Add the generated `audit-agents.yml` at path
   `.github/workflows/audit-agents.yml` (yes, `.github/` inside the `.github`
   repo). Commit to `main`.
3. In that repo: **Settings → Actions → General → Access** →
   *Accessible from repositories in the Trench-Sports organization*.

**Both repos are private, so if you skip 1.3 the `uses:` line resolves to a 404
and every PR check fails.** Do this before merging the new `audit.yml`.

## Step 2 — Org-level authentication

Currently the token is `CLAUDE_CODE_OAUTH_TOKEN`, generated by `claude
setup-token` and bound to one person's subscription. That's fine while you're
the only engineer and a silent single point of failure the moment you aren't.

The reusable workflow accepts either credential and fails fast when neither is
present, so you can migrate without touching YAML again:

1. **Now:** Org → Settings → Secrets and variables → Actions → New organization
   secret → `CLAUDE_CODE_OAUTH_TOKEN`. Set repository access to *Selected* and
   pick `Trench-Sports-FrontEnd`. Delete the repo-level copy afterward so
   there's one source of truth.
2. **When a second engineer joins:** create an API key in the Anthropic Console,
   add it as org secret `ANTHROPIC_API_KEY`, and remove the OAuth secret. No
   workflow change needed.

Org secrets are not inherited automatically — each secret has its own repo
access list, and a repo not on the list sees an empty string.

## Step 3 — Enable Code Review

Requires Owner or Primary Owner on the Claude organization, plus permission to
install GitHub Apps on the GitHub org.

1. Go to https://claude.ai/admin-settings/claude-code → **Code Review** → Setup.
2. Install the Claude GitHub App on `Trench-Sports`. Grant it
   `Trench-Sports-FrontEnd` at minimum. The same app powers `@claude`, so
   installing it here also covers `claude.yml`.
3. Select `Trench-Sports-FrontEnd` in the repositories table.
4. Set **Review Behavior** to **Once after PR creation**, not *After every
   push*. Reviews average $15–25 each and per-push multiplies that by your
   commit count on a branch. Push-triggered review is worth revisiting once you
   see real numbers.
5. Set a monthly cap at https://claude.ai/admin-settings/usage for the Claude
   Code Review service. Without one, a bad week of large PRs has no ceiling.

Code Review bills to **usage credits**, separately from the plan's included
usage. It never blocks a merge — the check run always completes neutral.

### Overlap with the audit agents

Both now comment on every PR, and `REVIEW.md` deliberately restates several
concerns the auditors already cover (RLS scoping, unbounded payloads,
telemetry PII). That duplication is intentional for the first few weeks —
it tells you which of the two actually catches things in this codebase. After
~10 PRs, look at what each found that the other missed and narrow `REVIEW.md`
to the gap. Paying twice for the same finding indefinitely is the failure mode
to watch for.

## Step 4 — Assigning issues to agents

This is the piece I could not verify. GitHub's Agent HQ docs page is
client-rendered and returned empty, and browser page-reading was unavailable in
the session where this was written, so the setup below is **unconfirmed** —
treat it as a starting point, not instructions.

What is confirmed and works today, without Agent HQ: `claude.yml` already
handles `issues: [opened]`, so writing `@claude` in an issue body starts a run
that can open a PR. That covers most of what "assign an issue to an agent"
means in practice.

To check the org-level surface: **Org → Settings → Copilot → Coding agent**
(naming may differ), and confirm which third-party agents your plan exposes.

---

## Verification

After steps 0–3, open a throwaway PR against `main` with a one-line change to
something the auditors watch — a new `.from(...)` call in `src/` will do it.
Expect:

- an **Audit** check running the 7 agents, uploading `audit-findings`
- a **Claude Code Review** check run, neutral conclusion, with inline comments
- `@claude what does this PR change?` in a comment producing a reply

If Audit fails immediately with a workflow-not-found error, step 1.3 was
missed. If it fails at "Fail early if no credential is present", the org secret
exists but `Trench-Sports-FrontEnd` isn't on its repository access list.
