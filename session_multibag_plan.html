Fan-out — one phone, three bags
Three-bag BLE constraint analysis
connections iOS allows ~7 simultaneous BLE centrals; Android typically 4–7 depending on chipset. Three bags is well within both. We never approach the cap — but we cap our own UI at 6 to leave headroom for the future heart-rate strap and the laser timing gate. 3 / ~7
throughput Model II (25 Hz, ~60 B/frame) = 1.5 KB/s per bag. Model III (120 Hz batch, ~600 B/packet @ 8 Hz) = ~5 KB/s per bag. 3 × Model III = 15 KB/s aggregate — well below the ~50 KB/s practical ceiling at conn interval 15 ms. 15 KB/s
conn interval Each link gets its own interval. The OS schedules connection events round-robin. With 3 links at 15 ms interval, each gets a 5 ms slot — adequate for current frame sizes. We don't need to negotiate intervals. 15 ms
parallel writes Phone → ESP32 writes (START, STOP, MODE) are independent per link. Firing three writeUtf8() calls without await in between hits the BLE stack as parallel queued ops — ~5–15 ms total spread instead of 3 × interval. Critical for sync. ~10 ms skew
RSSI bookkeeping Each connection has its own RSSI sample. UI shows per-bag bars so the coach can see one bag drifting before it disconnects. Native adapter exposes RSSI on the periodic scan; we poll at 1 Hz while connected. 1 Hz
Identifying A vs B vs C
primary key The obj.id field on the hello packet (e.g. tsii-7c9a) is the only stable identifier — it survives reboots, name changes, and re-pairing. This is what we already write to devices.id in Supabase (see handleNotify @ session.tsx:2066). Use it as the slotId source of truth. hello.id
display label BLE advertised name (TS-7C9A or MPY-7C9A) is what the coach sees in the picker and on each bag card. It can be renamed by the firmware, so never use it as a key. We already filter the picker by name prefix via getBleNamePrefixes().all. BLE name
slotId Phone-assigned. Either reuse hello.id verbatim (simplest) or generate slot_a / slot_b in order of connection. The latter survives a swapped bag in the same physical position; the former is portable across sessions. Recommendation: use hello.id — one less mapping table to maintain. = hello.id
athlete binding Athlete-to-slot mapping is set by the coach in the device manager panel (Tab 4). Stored on the SlotState.athleteId field. Bags can be re-assigned between sessions without touching the slotId. user-set
Why hello.id and not BLE name The BLE-name approach was tempting because the user already sees it in the picker. But we already had a near-miss in production where a firmware update changed the name prefix from TS- to MPY- and broke device claiming. The obj.id field is generated from the ESP32's MAC and never changes — same value the devices table already uses as its primary key.

The full SlotState type
type SlotId = string;  // = hello.id, e.g. "tsii-7c9a"

interface SlotState {
  // ── identity ──────────────────────────────────────────────────────────
  id:           SlotId;            // = hello.id, source of truth
  bleName:      string;            // "TS-7C9A" — display only
  athleteId:    string | null;     // coach-assigned in device manager
  athleteName:  string | null;     // cached for header rendering

  // ── connection (was: connRef, assemblerRef, deviceInfoRef) ───────────
  conn:         AdapterConnection | null;
  assembler:    ChunkAssembler;    // per-slot — frames don't interleave
  device:       DeviceInfo | null; // hw, fw, scanPeriodMs, samplingHz
  rssi:         number | null;     // dBm, polled at 1 Hz
  status:       "connecting" | "connected" | "disconnected" | "error";

  // ── per-slot mode (was: sessionMode + sessionModeRef) ────────────────
  mode:         SessionMode;        // "power" | "reaction" | ... — per-bag override

  // ── capture buffer (was: framesRef, frameIndex) ──────────────────────
  frames:       BleFrame[];
  frameIndex:   number;

  // ── mode timers (was: rxTimer, tgtTimer, volTimer, volTickTimer) ────
  timers: {
    rx:       ReturnType<typeof setTimeout> | null;
    tgt:      ReturnType<typeof setTimeout> | null;
    vol:      ReturnType<typeof setTimeout> | null;
    volTick:  ReturnType<typeof setInterval> | null;
  };

  // ── reaction (was: rxPhaseRef, rxSignalAt, rxSumMs, rxAttemptsRef) ──
  rx: { phase: string; signalAt: number | null; sumMs: number; attempts: number; bestMs: number | null; };

  // ── target (was: tgt* family @ session.tsx:1813-1824) ────────────────
  tgt: { phase: string; zone: ZoneTarget | null; signalAt: number | null; sumMs: number; correctSumMs: number; attempts: number; hits: number; bestAllMs: number | null; bestCorrectMs: number | null; };

  // ── volume (was: vol* family @ session.tsx:1787-1795) ────────────────
  vol: { phase: string; signalAt: number | null; windowEndsAt: number | null; sum: number; attempts: number; hits: number; windowIdx: number; windowHitSeq: number; };

  // ── accuracy (was: accHitsRef, accSumRef) ────────────────────────────
  acc: { hits: number; sum: number; avg: number; };

  // ── per-frame stamps (was: pending*Ref family @ ~1851-1857) ──────────
  pending: { rxMs: number | null; tgtZone: ZoneTarget | null; tgtCorrect: boolean | null; volWindowIdx: number | null; volHitSeq: number | null; };
}
The createSlot() initializer
// Called from connectBle() after a successful hello packet arrives.
// The hello.id is the slotId — see session.tsx:2066 where it's already
// extracted for the devices table upsert.
function createSlot(hello: { id: string; fw: string; hw?: string; mode?: string; rows: number; cols: number; },
                    bleName: string,
                    conn:    AdapterConnection): SlotState {
  const isModelIII = hello.hw === "III";
  return {
    id:          hello.id,
    bleName,
    athleteId:   null,
    athleteName: null,
    conn,
    assembler:   new ChunkAssembler(),
    device: {
      id:           hello.id,
      fw:           hello.fw,
      hw:           hello.hw ?? "II",
      rows:         hello.rows,
      cols:         hello.cols,
      mode:         hello.mode ?? "single",
      scanPeriodMs: isModelIII ? 8  : 37,
      samplingHz:   isModelIII ? 120 : 25,
    },
    rssi:        null,
    status:      "connected",
    mode:        sessionModeGlobal,    // inherit from global picker; can be overridden per-bag
    frames:      [],
    frameIndex:  0,
    timers:      { rx: null, tgt: null, vol: null, volTick: null },
    rx:          { phase: "idle", signalAt: null, sumMs: 0, attempts: 0, bestMs: null },
    tgt:         { phase: "idle", zone: null, signalAt: null, sumMs: 0, correctSumMs: 0,
                   attempts: 0, hits: 0, bestAllMs: null, bestCorrectMs: null },
    vol:         { phase: "idle", signalAt: null, windowEndsAt: null, sum: 0,
                   attempts: 0, hits: 0, windowIdx: 0, windowHitSeq: 0 },
    acc:         { hits: 0, sum: 0, avg: 0 },
    pending:     { rxMs: null, tgtZone: null, tgtCorrect: null, volWindowIdx: null, volHitSeq: null },
  };
}

Why a Map and not an object Map preserves insertion order (so "first connected" → top of the panel works naturally), gives us O(1) get/set/delete, and iterates cleanly with for (const [slotId, slot] of slotsRef.current). A plain object would technically work but loses iteration ergonomics and tempts you to use the slotId as a key without thinking about whether the key is safe (it is — but Map signals intent).
One subtlety: React state vs ref for the slot map The mutable source of truth lives in slotsRef.current (ref pattern — same reason captureRef exists at 1842). For rendering, mirror it into a state map updated via setSlots(new Map(slotsRef.current)) after any mutation that affects the UI. This is the same dual-write pattern already used for volHitsRef + setVolHits at 2183-2184.
The key insight
One handleNotify per slot — slotId captured by closure, slot state read from ref adapterStartNotifications(conn, TX, (val) => handleNotify(slotId, val)) — the slotId is a string primitive closed over at subscription time. Strings are immutable, so the captured value can't go stale. Inside handleNotify, all mutable slot data is read fresh via slotsRef.current.get(slotId) — the same ref-pattern handleNotify already uses today for captureRef.current and sessionModeRef.current (see session.tsx:2031, memoised with useCallback([])).

Why the closure is safe
slotId String primitive, captured at subscribe time. JS strings are immutable — slotId inside the arrow body always equals the value at the time adapterStartNotifications was called. No state, no ref, nothing to go stale. This is the central trick of the whole refactor. immutable
slotsRef.current.get(slotId) Fresh read every frame. slotsRef is the same kind of ref as captureRef — React doesn't re-create it across renders, so the contents are always current. The slot itself is a mutable object; mutating its fields mutates what every future .get() returns. always current
captureRef · startTimeRef · sessionIdRef Stays exactly as today. These are session-global and already follow the ref pattern. handleNotify reads them at 2141/2245/2258 the same way it always has. unchanged
disconnect mid-frame Self-healing. If the slot was removed from the Map between when the BLE notification fired and when we processed it, slot is undefined and we early-return. No crashes, no orphan state. safe
Broadcast vs targeted commands
broadcast START_SYNC, STOP_SYNC, OTA "ota_begin" — iterate slotsRef.current.values(), fire writeUtf8(slot.conn, payload) with no await between writes, then Promise.allSettled() to confirm delivery. Same skew-minimisation trick as the sync-mechanics doc: parallel BLE writes hit the connection-interval floor (~7.5–15 ms) instead of stacking sequentially. all slots
targeted Per-bag MODE change, individual STOP, RSSI poll, OTA "ota_data" chunks — const slot = slotsRef.current.get(slotId); await writeUtf8(slot.conn, payload). Single write, awaited normally. one slot
conditional Save sheet — coach can toggle which bags to save. Filter slotsRef.current.values() by the toggle state, then Promise.all(filtered.map(uploadSession)). One Supabase session row per bag (athlete-attributed). subset 
// Broadcast helper — matches the sync-mechanics pattern
async function broadcastToAllSlots(payload: string): Promise<void> {
  const writes: Promise<void>[] = [];
  for (const slot of slotsRef.current.values()) {
    if (slot.status !== "connected") continue;
    writes.push(writeUtf8(slot.conn!, RX, payload));   // no await ← key
  }
  await Promise.allSettled(writes);
}

// Targeted helper
async function sendToSlot(slotId: SlotId, payload: string): Promise<void> {
  const slot = slotsRef.current.get(slotId);
  if (!slot?.conn) return;
  await writeUtf8(slot.conn, RX, payload);
}

Three separate setTimeout chains, three separate clears Today's cleanup at session.tsx:2023-2026 clears one set of timers when sessionActive flips false: clearTimeout(rxTimer.current), clearTimeout(tgtTimer.current), etc. With per-bag modes, each slot can have its own active timer chain — Bag A counting down to a reaction signal while Bag B is mid-target-result.

Global vs per-bag controls

global — top bar

  • Start all / Stop all — broadcasts START_SYNC / STOP_SYNC.
  • Session mode picker — sets the default for newly connected slots. Doesn't override active slots.
  • Session timer — single global elapsedMs, fed by the existing startTimeRef.
  • Save sheet — opens the per-bag confirmation panel.

per-bag — inside each card

  • Mode chip — taps open a per-slot mode picker. Sends a targeted MODE command.
  • Athlete picker — assigns or swaps the athlete bound to this slot.
  • Force disconnect — drops just this slot, leaves others running.
  • Per-bag stats — RT, hits, peak mV, accuracy — pulled from this slot's SlotState.
